## 부족한 점 (빈도순)
1. **AI가 화면에 없다 (5/5).**
   - Claude 호출 설정(모델 ID, 키, 실패 시 대체 경로)이 설계에 없었다. 게다가 builder 규칙이 "모델 ID 추측 금지"였다. 그래서 규칙 기반 데모만 나왔고, 화면에 "rules mode"나 "cache"가 그대로 보이기도 했다.
   - AI Must가 마지막 단계로 밀려 결국 만들지 못했다.
2. **행사·미션 조건이 고정돼 있다 (4/5).** `/brief`에 우리 행사 조건이 박혀 있었다. 미션별 심사 기준이나 필수(스폰서) 기술을 받을 칸이 없었고, ideate에 미션 적합성과 AI 깊이 축이 없었다.
3. **차별성이 늘 최하 축이다.** ideate가 스스로 매긴 점수는 낙관적이었다(3.8 대 실제 리뷰 3.1). 경쟁 서비스 확인이 없었다. 4번과 5번이 둘 다 "프리랜서 계약서"로 모였다. 같은 예시 미션을 받은 다른 팀도 같은 답을 낼 가능성이 높다.
4. **가치 숫자에 근거가 없다.** 우리 숫자는 우리가 정한 규칙으로 계산한 것이다. 우승작 CrossBeam은 외부 근거가 있는 숫자를 썼다. 덱 숫자와 화면 숫자가 서로 달랐고, 건당 API 원가 계산도 없었다.
5. **포트와 경로가 하드코딩돼 있다.** 8000, 5173, `C:\project\planning-harness`가 여러 파일에 직접 적혀 있었다.
6. **`/prd`가 `requirements.md`를 거의 1:1 복사한다.** 토큰 낭비이고 두 문서가 어긋날 위험이 있다.
7. **Railway 배포가 강제되고 로컬 모드가 없다.** Dockerfile도 항상 필수였다.
8. **사전 점검이 없다.** Python Playwright 미설치를 확인하지 않았다. 서버 시작·종료 규칙이 없어서 Stop-Process가 자기 셸까지 죽였다.
9. **judge-review 입력이 불명확하다.** WebFetch로 SPA나 localhost를 열면 빈 화면이 나온다. 스크린샷 표준 경로가 없었고, judge 에이전트를 못 띄울 때의 대체 절차도 없었다.
10. **사람과 builder 담당이 겹친다.** 둘 다 `frontend/`를 맡았다. 프런트 담당은 `api.md`가 나올 때까지 놀았다. 리뷰 후 덱을 다시 쓰는 단계도 없었다.
11. **10:45~11:05에 승인 멈춤과 설치가 몰린다.**
12. **`grill-me`가 동작하지 않는다.** `grilling`이 user-invocable-only라 Skill 호출이 막혔다. 헤드리스 테스트에서 모델이 파일을 직접 읽는 우회를 했다.

## 잘 된 점
- 기능 ID(M1…)가 requirements에서 qa까지 끊김 없이 이어졌다.
- 실행할 수 있는 qa 완료 조건이 그대로 테스트 스크립트가 됐다.
- 단일 서비스 설계(FastAPI가 `dist`를 서빙, 상태 기반 화면 전환)가 문제없이 동작했다.
- "2명 이상 지적이면 수정 1순위" 규칙 덕분에 우선순위가 빨리 정해졌다.
- 멈추는 곳 3개에 추천 답이 붙어 있어 기획이 빨랐다.
