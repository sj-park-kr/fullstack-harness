# 빌드 계획

Matt Pocock의 `prd-to-plan`(MIT, 현재 `to-tickets`)을 해커톤 오케스트레이터용으로 고쳤다. 수직 슬라이스 원칙은 그대로 두고, 단계마다 에이전트 배치를 붙인다.

## 절차
1. `docs/prd.md`, `docs/architecture.md`, `docs/api.md`가 없으면 빠진 단계(`/prd`, `/design`)를 안내하고 멈춘다. 긴 문서는 헤더 단위로 필요한 구간만 읽는다.
2. 모든 단계가 공유할 고정 결정(경로, 데이터 모델, 디렉터리 구조)을 설계 문서에서 뽑아 머리말에 둔다.
3. 필수(Must) 기능을 수직 슬라이스로 나눈다(아래 규칙). Nice 기능은 마지막 단계들로 따로 둔다.
4. 단계 목록(제목, 기능 ID, builder 배치)을 번호 목록으로 보여 주고 묻는다: 크기가 적당한지, 합치거나 쪼갤 단계가 있는지. 승인될 때까지 고친다.
5. 아래 템플릿으로 `docs/plan.md`를 쓰고 `docs/index.md`에 링크를 추가한다.
6. 다음 단계로 `/fullstack-orchestrator`를 안내한다.

## 수직 슬라이스 규칙
- 단계마다 화면 → API → 데이터까지 좁지만 끝까지 이어지는 경로를 만든다. 한 층만 만드는 가로 단계는 만들지 않는다.
- 끝난 단계는 혼자서 데모하거나 확인할 수 있어야 한다.
- 1단계는 뼈대: 백엔드 `/health`와 그것을 호출해 보여 주는 프런트 화면 하나로 끝까지 연결한다.
- 두꺼운 단계 몇 개보다 얇은 단계 여러 개가 낫다. 단계 하나는 builder 한 명이 새 컨텍스트에서 끝낼 크기다.
- 바뀌기 쉬운 함수·파일 이름은 쓰지 않는다. 경로, 스키마, 모델 이름 같은 고정 결정은 쓴다.

## 에이전트 배치 규칙
- builder 수는 1~3. 대부분 2(백엔드 `backend/`, 프런트엔드 `frontend/`)를 병렬로 둔다.
- 병렬 builder끼리 담당 디렉터리가 겹치면 안 된다. 상위·하위 경로도 겹침이다(`backend/`와 `backend/app/`).
- 공유 파일(`docs/api.md`, 루트 설정 등)을 고쳐야 하면 그 단계는 순차로 하거나 한 builder에게만 맡긴다.
- 병렬 builder는 `docs/api.md` 계약만 보고 따로 일한다. 계약이 없는 단계는 순차로 둔다.
- 완료 조건은 qa가 실제로 실행해 확인할 수 있는 동작으로 쓴다(요청과 기대 응답, 클릭과 기대 화면).

## 템플릿

오케스트레이터가 읽는 형식이다. 헤더와 키 이름(`- 상태:` 등)을 바꾸지 않는다. 상태는 `대기`, `완료` 중 하나다.

```md
# Plan: <서비스 이름>

> 출처: docs/prd.md, docs/architecture.md, docs/api.md

## 고정 결정
- 경로: ...
- 데이터 모델: ...
- 디렉터리: backend/ (FastAPI), frontend/ (React)

---

## Phase 1: <제목>
- 상태: 대기
- 목표: <이 단계가 끝나면 데모에서 되는 것 한 문장>
- 기능: M1
- 실행: 병렬
- builder 수: 2

| builder | 담당 디렉터리 | 할 일 |
| --- | --- | --- |
| backend | backend/ | ... |
| frontend | frontend/ | ... |

### 완료 조건 (qa)
- [ ] ...

---

## Phase 2: <제목>
...
```
