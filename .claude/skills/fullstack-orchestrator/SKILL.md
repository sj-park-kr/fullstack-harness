# 풀스택 오케스트레이터

## 실행 모드: 서브에이전트 위임

메인 세션은 조율만 한다. 파일 탐색, 구현, 검증은 서브에이전트에 맡겨 메인 세션의 컨텍스트와 비싼 모델 사용을 줄인다.

## 에이전트와 모델

| 작업 | `subagent_type` | 모델 | 이유 |
| --- | --- | --- | --- |
| 파일·코드 위치 찾기, 문서 조사, 로그 요약 | `scout` | haiku | 판단이 적은 읽기 작업. 가장 싸다 |
| 범위가 정해진 기능 구현(백엔드·프런트) | `builder` | sonnet | 해커톤 작업의 대부분. 속도와 품질 균형 |
| 서비스 구조·API 계약 설계, builder가 두 번 실패한 버그 | `architect` | opus | 깊은 추론이 필요한 소수 작업에만 |
| 기능 완성 직후 검증, 제출 전 데모 점검 | `qa` | sonnet | 정해진 절차 실행과 결과 대조 |

모델은 각 에이전트 정의 파일의 `model:`에 고정되어 있다. 호출할 때 `model`을 따로 넘기지 않는다.

## 토큰 절약 규칙

1. **메인 세션이 직접 하는 일**: 한두 줄 수정, 이미 아는 파일 한 개 확인, 사용자와의 대화. 위임하는 비용이 더 크기 때문이다.
2. **나머지는 위임한다.** 특히 여러 파일을 읽어야 하는 탐색은 메인이 하지 말고 `scout`에 맡긴다.
3. **독립 작업은 한 메시지에서 병렬로 호출한다.** 예: 백엔드 builder와 프런트엔드 builder를 동시에.
4. **같은 파일을 두 에이전트가 동시에 고치게 하지 않는다.** `docs/plan.md`의 담당 디렉터리를 그대로 지정한다(보통 `backend/`, `frontend/`).
5. **결과는 짧게 받는다.** 각 에이전트는 요약과 파일 경로만 반환한다. 긴 내용은 `_workspace/`에 파일로 남긴다.
6. **`docs/plan.md`는 통째로 읽지 않는다.** Grep으로 `^## Phase`와 `- 상태:`를 찾고, 실행할 단계 구간만 읽는다.
7. **이미 맡긴 탐색을 메인이 다시 하지 않는다.** 완료 알림을 기다린다.
8. **프롬프트에 필요한 맥락을 다 넣는다.** 서브에이전트는 대화 기록을 모른다. 담당 디렉터리, 설계 문서 경로, 완료 조건을 적는다.

## 입력 문서
`docs/index.md`가 목록이다. `docs/prd.md`(기능 ID), `docs/architecture.md`, `docs/api.md`(API 계약), `docs/adr/`, `docs/plan.md`(실행 순서). 메인은 이 문서를 고치지 않는다(단계 상태 표시만 예외).

## 작업 절차

### 0단계: 기존 작업 확인
- `docs/plan.md`가 없으면 `/prd` → `/design` → `/build-plan`을 먼저 하라고 안내하고 멈춘다. 메인이 계획을 임의로 만들지 않는다.
- `- 상태: 대기`인 첫 단계부터 이어서 진행한다. 모두 `완료`면 4단계로 간다.
- 사용자가 일부만 고쳐 달라고 하면 해당 에이전트만 다시 호출한다.
- `caveman`, `ponytail` 외의 스킬은 사용자가 지정했을 때만 쓰고, 그 지침을 서브에이전트 프롬프트에 함께 넣는다.

### 1단계: 단계 읽기
현재 단계 구간에서 목표, 기능 ID, `실행`(병렬/순차), `builder 수`, builder 표(담당 디렉터리, 할 일), 완료 조건을 읽는다. 병렬인데 담당 디렉터리가 겹치면 실행하지 말고 사용자에게 알린다.

### 2단계: 구현
- 표의 행마다 `builder`를 하나씩 호출한다. 병렬이면 한 메시지에서 동시에, 순차면 표 순서대로 앞 결과를 받은 뒤 호출한다.
- 프롬프트에 넣을 것: 단계 목표, 그 행의 할 일, 담당 디렉터리(밖은 고치지 말 것), `docs/api.md`·`docs/architecture.md` 경로, 완료 조건, `ponytail`과 토큰 절약 규칙.

### 3단계: 검증(단계마다)
- 단계의 builder가 모두 끝나면 `qa`에 그 단계의 완료 조건을 그대로 넘겨 검증을 맡긴다. 마지막에 한 번만 검사하지 않는다.
- `qa`가 실패를 보고하면 재현 단계를 그대로 붙여 해당 디렉터리의 `builder`에게 수정을 맡기고 다시 `qa`를 부른다.
- 통과하면 `docs/plan.md`에서 그 단계의 `- 상태: 대기`를 `- 상태: 완료`로 Edit하고, 사용자에게 한 줄 보고 후 다음 단계로 간다.

### 4단계: 제출 전 점검
- `qa`에게 심사위원이 누를 핵심 흐름 전체를 Playwright로 점검하게 한다.
- 통과하면 사용자에게 데모 링크와 남은 위험을 보고한다.

## 데이터 전달
- 설계·계획 문서: `docs/`(git 포함, `docs/index.md`에서 링크)
- 중간 산출물: `_workspace/{단계}_{에이전트}_{내용}.md` (예: `phase2_qa_report.md`)
- QA 스크립트·스크린샷: `_workspace/qa/`
- `_workspace/`는 git에 올리지 않는다.

## 오류 처리
- 에이전트가 실패하면 한 번 다시 시도한다. 또 실패하면 누락 사실을 사용자에게 알리고 진행한다.
- `builder`가 같은 버그를 두 번 못 고치면 `architect`에게 넘긴다(에러 메시지, 시도한 내용 포함).
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 다시 해도 결과가 같고 크레딧만 쓴다. 어디까지 진행됐는지 확인해 사용자에게 보고한다.
- `.env` 접근이 훅에 막혔다는 메시지가 나오면 우회하지 않는다. `.env.example`의 변수 이름만 사용한다.

## 테스트 시나리오

### 정상 흐름
1. 사용자: `/fullstack-orchestrator` (`docs/plan.md` 있음, Phase 1 `대기`)
2. Phase 1(병렬, builder 2): 백엔드·프런트엔드 `builder` 동시 호출 → 각자 담당 디렉터리만 수정
3. `qa` → Phase 1 완료 조건 통과 → `상태: 완료`로 표시 → Phase 2 진행
4. 모든 단계 완료 → 4단계 제출 전 점검 → 메인이 사용자에게 요약

### 오류 흐름
1. `qa`가 "견적 생성 버튼 클릭 시 500 에러" 보고
2. `builder`(백엔드) 수정 시도 2회 실패
3. `architect`가 근본 원인 분석·수정(사용자가 `/systematic-debugging`을 지정했으면 그 지침 포함)
4. `qa` 재검증 → 통과
