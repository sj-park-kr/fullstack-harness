# PRD 작성

Matt Pocock의 `write-a-prd`(MIT, 현재 `to-spec`)를 해커톤용으로 고쳤다. 긴 인터뷰를 빼고, 입력 문서의 빈틈만 묻는다.

## 입력
- 인자로 받은 경로, 또는 대화에 붙여 넣은 텍스트.
- 둘 다 없으면 `C:\project\planning-harness\plan\requirements.md`가 있는지 확인한다. 없으면 사용자에게 경로나 내용을 달라고 하고 멈춘다. 내용을 추측해 채우지 않는다.
- 입력이 길면 전체를 읽지 않는다. Grep으로 헤더를 찾아 필요한 구간만 읽는다.

## 절차
1. 입력에서 문제, 대상 사용자, 핵심 기능, 데모 흐름, 제약(시간, 기술, 심사 기준)을 뽑는다.
2. 빈틈이나 모호한 점이 있을 때만 질문한다. 한 번에 최대 3개, 각 질문에 추천 답을 붙인다. 입력으로 답할 수 있는 것은 묻지 않는다.
3. 아래 템플릿으로 `docs/prd.md`를 쓴다. 이미 있으면 바뀐 부분만 Edit으로 고친다.
4. `docs/index.md`에 PRD 링크를 추가한다(없으면 만든다).
5. 사용자에게 필수 기능 목록과 경로만 짧게 보고하고, 다음 단계로 `/design`을 안내한다.

## 범위 원칙
- 7시간 해커톤이다. **필수(Must)** 는 심사위원 앞 데모 흐름 1개를 끝까지 돌리는 데 꼭 필요한 기능만 둔다. 보통 3~5개.
- 나머지는 **있으면 좋음(Nice)** 으로 내린다. 애매하면 Nice로 둔다.
- 기능에 ID(`M1`, `N1`)를 붙인다. `/build-plan`이 이 ID로 단계를 묶는다.
- 파일 경로, 코드, API 상세는 쓰지 않는다. 그것은 `/design`이 정한다.

## 템플릿

```md
# PRD: <서비스 이름>

> 출처: <입력 경로 또는 "대화 입력">

## 문제
사용자 관점의 문제.

## 해결
사용자 관점의 해결책 한 문단.

## 데모 시나리오
심사위원 앞에서 보여 줄 흐름 1개를 번호 단계로(5~8단계).

## 필수 기능 (Must)
| ID | 기능 | 사용자 스토리 | 완료 기준 |
| --- | --- | --- | --- |
| M1 | ... | <사용자>로서 <기능>을 원한다, <이유> 때문에 | 데모에서 확인할 수 있는 동작 |

## 있으면 좋음 (Nice)
| ID | 기능 | 메모 |
| --- | --- | --- |
| N1 | ... | ... |

## 범위 밖
하지 않을 것.

## 가정과 미결 사항
질문으로 확정하지 못한 가정.
```
